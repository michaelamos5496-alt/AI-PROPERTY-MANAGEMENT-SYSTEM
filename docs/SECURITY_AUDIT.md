# Security audit (Phase 8)

Scope: authentication and sessions, row level security and organization isolation, endpoint authorization, file access, webhook verification (WhatsApp, billing), AI tool permissions and prompt injection, approval integrity, secrets, dependencies, rate limits, injection/XSS/CSRF/redirects/mass assignment, logging.
Method: read the code and SQL, then turn every claim into a test that fails if the claim stops being true. **This was done by the people who built the system, with automated tools. It is not an independent penetration test** and must not be described as one.
No real customer data was used anywhere; all tests run on synthetic data in disposable databases.

## What is proven by tests (re-run on every change: `npm test`)

| Claim | How it is checked | Test |
|---|---|---|
| Every table has row level security; signed-in users cannot write any table directly; anonymous users have no privilege on any table, view or sequence | catalog queries over `pg_class` / privileges | `tests/security/db-invariants.test.ts` |
| Anonymous users can execute **no** function in `public` or `app`; service-only (`*_svc_*`) functions are executable by the service role and by **no** signed-in user | `has_function_privilege` over all functions | same |
| Only a reviewed allow-list of internal helpers is callable by signed-in users; every SECURITY DEFINER function pins `search_path` | catalog queries | same |
| **Every** organization-scoped database function (157) refuses a stranger, an anonymous caller, and a member of a *different* organization addressing this one; 80+ data-changing functions refuse a view-only member; refusals are real authorization refusals, not malformed arguments | each function is called with typed dummy arguments as each actor; denial codes are classified | `tests/security/rpc-authz.test.ts` |
| Every declared API endpoint (135 definitions) returns 403 below its minimum role, 404 to non-members and to other organizations' owners, 401 anonymously, and lets the minimum role in; every hand-written route is in a reviewed list so a new route cannot ship unreviewed | route inventory × 7 actors; static scan of route files | `tests/api/authz-matrix.test.ts` |
| Changing identifiers cannot reach another organization: every endpoint, addressed through the attacker's organization, with every one of the victim's real record ids (500+ requests incl. mutating ones), returns no 2xx, leaks no marker string, and leaves the victim's data byte-identical | marker-string sweep + before/after snapshot | `tests/api/attack-surface.test.ts` |

## Findings and what was done

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | **Functions in the internal `app` schema were executable by PUBLIC** (so by anonymous and signed-in users) because a schema-level `alter default privileges … revoke` cannot remove Postgres's built-in default grant. Not reachable through the API as long as the `app` schema is not exposed (it is not by default), but one dashboard setting away from being reachable. Found by the new catalog invariants. | Medium (defense in depth) | **Fixed**: migration `20261021000001` revokes all and re-grants only what policies/defaults need; database default privileges now deny PUBLIC for new functions; tests assert it; `supabase/config.toml` and CI assert only `public` is exposed; DEPLOYMENT.md tells operators never to expose `app` |
| 2 | **Open redirect after login**: `safeNext` accepted `/<TAB>/evil.com`, which browsers normalize to `//evil.com`. | Medium | **Fixed** (plain path characters only) + test |
| 3 | Staff listing approvals without a scope were refused (default was the manager-only inbox) | Low (availability of a feature) | **Fixed** (role-appropriate default) |
| 4 | Cancelling another user's AI conversation answered `200 {requested:false}` instead of 404 | Low (consistency; no data exposed) | **Fixed** |
| 5 | **Cost-based denial of service**: organization-wide finance lists recomputed every charge's balance on each call (~450 ms for 33,000 charges; 20 simultaneous users saturated a CPU). | Medium (availability) | **Fixed**: balances are cached in `charge_balances` by triggers and *proved equal to the ledger by `reconcile_finance` and a randomized property test*; list queries made single-pass (3–6× faster); role-level `statement_timeout` / idle-transaction timeouts (migration `20261023000001`). Remaining capacity limits in LOAD_TEST_RESULTS.md |
| 6 | Health check was a constant `{ok:true}` (would not notice a dead database, stuck queues or a stopped scheduler) | Low | **Fixed**: readiness, authenticated deep health with queue/dead-letter counts, live integration probes, scheduler heartbeat, alert webhook |
| 7 | `maxDuration` 15 s on Vercel while an AI turn may run 50 s | Low (reliability) | **Fixed** in `vercel.json` (60 s; operator must match their plan) |
| 8 | Billing checkout URL from the provider was not host-checked before the browser navigated to it | Low | **Fixed** (only `*.paystack.com/.co` over https) |
| 9 | Dev toolchain: `vitest`/`tinypool` had critical advisories (prototype-pollution → RCE gadget in test workers; not shipped, not reachable from the app) | Low for production, Critical for developer machines/CI | **Fixed** (vitest 5, esbuild 0.28); `npm audit` reports 0 |

Reviewed and found sound (no change): all dynamic SQL (`execute format`) uses whitelisted column names with `%I`, direction through a whitelist, values through bind parameters; no `innerHTML`-style sinks; cookie flags; webhook signature comparisons are constant-time over raw bytes; service-role key is used only by narrow `*_svc_*` functions and background workers; error responses contain no stack traces or internals; logs redact secrets and mask phone numbers.

## Residual risks and limitations (not fixed; know them)

1. **Rate limiting is per server instance (in memory).** On serverless, a distributed attacker is slowed, not stopped. Supabase Auth has its own limits; add Vercel Firewall/WAF rate rules (or a shared store such as Upstash) for the login, registration, webhook and AI endpoints before opening signups widely.
2. **No multi-factor authentication** for staff, and no "sign out everywhere" screen. Owners/admins control money and tenants' data; enable MFA when Supabase Auth's MFA is wired in, or put SSO in front for larger customers.
3. **Uploads:** type allow-list (PDF/PNG/JPEG/DOCX/WebP), 10 MB limit, signed one-time upload and 60-second download URLs, served as attachments; the declared content type is not verified by inspecting file bytes and there is **no malware scanning**. Staff download files tenants upload: add scanning (e.g. ClamAV or a scanning API) before enabling tenant photo uploads for untrusted audiences.
4. **Prompt-injection detection is heuristic.** The controls that matter are structural (the model can only read and *propose*; a person confirms or a manager approves; message text is pinned to the draft a person read; tool results are labelled untrusted). An adaptive attacker may still make the assistant say something misleading to staff; it cannot make it act.
5. **WhatsApp:** unverified senders can learn whether a property name or unit reference exists (needed to log a report). Sender identity depends on the one-time code and on WhatsApp's own account security (SIM-swap risk is why links expire after 180 days and balances are only shown to verified numbers).
6. **Supply chain:** `npm audit` finds known vulnerabilities only; there is no provenance/SBOM and no pinned CI action SHAs. Pin actions by commit SHA and enable Dependabot/Renovate.
7. **Secrets:** the Supabase service-role key bypasses row level security by design; whoever holds it holds everything. Restrict who can read Vercel Production variables; rotate on staff changes.
8. **Tenant isolation is demonstrated by tests, not formally verified.** The sweeps are broad (every function, every route, id tampering) but new code can add new paths: the route inventory and function sweeps fail when something unreviewed appears, which is the safety net.
9. **Providers are trusted for what they send, within signatures:** Meta and Paystack signatures prove origin, not intent; billing amounts are checked against our own price table; Paystack request shapes and recurring support for GHS/KES are not verified against a live account (BILLING.md).
10. **Not yet independently reviewed.** Commission a third-party penetration test of the staging environment before taking real tenant data at scale.
